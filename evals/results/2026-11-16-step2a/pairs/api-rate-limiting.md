# Rate limiting a public API for bursty clients across three regions

Chosen as the swarm's widest win. Problem `api-rate-limiting`.

## Problem

A company runs a public HTTP API in three regions behind a single global hostname; a client's consecutive requests can land in different regions. Paying plans allow between 600 and 6,000 requests per minute, free accounts 60. Many legitimate clients are bursty: a scheduled job may send its whole minute's allowance in two seconds and then go quiet. The team has been asked to add rate limiting that adds no more than about five milliseconds to a request and that never takes the API down when the limiter's own storage is slow or unavailable.

Design the rate limiter: the algorithm and why it fits bursty clients, where its state lives and how the three regions share a customer's quota, what happens when that state is slow or unreachable, and how clients learn their limits and when to retry. Be explicit about what the design gets wrong and by how much.

### Constraints

- The API runs in three regions behind one global DNS name; a client's requests may land in any region.
- Paying customers are limited by plan (for example 600 requests per minute); free clients to 60 per minute.
- Legitimate clients are bursty: a client may send its whole minute's quota in two seconds, then nothing.
- The limiter must not add more than about five milliseconds to a request, and the API must keep serving if the limiter's storage is unavailable.

### Success criteria

- A named limiting algorithm and why it suits bursty clients better than the alternatives.
- Where the limiter's state lives, how three regions see one customer's quota, and what inaccuracy that implies.
- What happens when the state store is slow or down, and what the client sees.
- How a client learns its limit and when to retry.

## Swarm answer

_Run `01a1e1cf-8612-7ab4-b493-069bb38d90b1`, 12 rounds, completed/budget_rounds, $0.0215, confidence 0.60; the final write-up, asked for about 900 words, 531 written._

Recommendation: enforce each customer's limit with a token bucket whose capacity equals the per-minute quota (600 for paid plans, 60 for free) and whose refill rate is the quota divided by 60 tokens per second. Each region keeps a local in-memory bucket per customer, so the request path performs only a local atomic decrement, adding about 0.1 ms, well inside the 5 ms budget. Regions ship consumption deltas asynchronously to a shared central store (for example Redis Cluster) and absorb other regions' deltas on a short replication cycle. This design is fast and available but approximate, and the approximation is stated below rather than hidden.

Why a token bucket: a full bucket lets a bursty client spend its entire minute's allowance in about two seconds and then wait for refill, which matches the scheduled-job pattern. A fixed window can reject a legitimate burst that straddles a window boundary and wastes unused quota at each boundary. A sliding window log needs per-request timestamps that are costly to store and share across regions within a 5 ms budget. A sliding window counter needs atomic updates to two adjacent bins, adding cross-region coordination that a single-key token bucket avoids.

What the design gets wrong: because each region holds a full-capacity bucket, a client spreading requests across three regions can be admitted up to roughly 3N in a burst before deltas sync, so the global limit is only enforced after replication catches up. Over-admission is bounded by replication lag times the request rate per region. For a 6,000/min customer at about 100 requests/s with a 50 ms lag this is on the order of 15 extra requests (about 0.25% of quota) per burst event, rising to about 2N in the worst simultaneous multi-region burst. These are bounded, accepted inaccuracies, not an exact limit. Assumption: the 50 ms lag is an estimate and must be measured; if real lag is seconds, the over-admission bound grows proportionally.

Client view: every response carries RateLimit-Limit, RateLimit-Remaining and RateLimit-Reset, where Remaining is a per-region local estimate and may be optimistic by up to the concurrent admissions of other regions. A 429 response with Retry-After is the only global truth. Clients should use exponential backoff with jitter, rely on 429 for hard limits, and not schedule traffic from the Remaining value alone. Assumption: reset semantics (per region or per customer) are fixed in the API contract as per customer, with Remaining documented as advisory.

Failure behaviour: the store call gets a timeout well inside the 5 ms budget and is guarded by a circuit breaker that trips when store latency exceeds about 2 ms. While tripped, each region falls back to a local limiter set to a plan-proportional share of the quota, assumed to be 1% to 5% of the plan maximum (roughly 60 to 300 requests per minute per region for a 6,000/min customer, so up to about three times that across regions). This bounds abuse during an outage to a stated multiple of the legitimate burst allowance and never takes the API down, though it can admit more than the global limit for the duration of the outage. The fallback percentage and breaker threshold need load testing before launch.

## Baseline answer

_claude-sonnet-5-5, asked for about 900 words, used 2109 of 2694 output tokens allowed under a $0.0300 cap, cost $0.0232. Board handles are shown here; the judge saw the answers with them removed._

**Recommendation:** use a token bucket per customer, enforced in each region against a local in-memory replica of the customer's state, with quota shared across regions by asynchronous, periodic exchange of consumption rather than a synchronous global counter. Fail open when the shared layer is slow or down, degrading to a conservative local-only limit. Tell clients their limits in standard headers and give them a precise Retry-After on every rejection.

**Algorithm: token bucket.** Each customer has a bucket with capacity B and refill rate R. A 600/min plan refills 10 tokens per second; a request costs one token. Capacity is the key tuning knob: set B equal to the plan's per-minute allowance (600, 6,000, 60 for free). That means a scheduled job can spend its entire minute's quota in two seconds, then wait for refill, and is never rejected for behaving legitimately. Alternatives fit worse. A fixed window counter permits double the allowance across a boundary (full quota at 0:59, full again at 1:00) and punishes nothing smooth. A sliding window log is exact but stores a timestamp per request, which is expensive at 6,000/min. A sliding window counter smooths the boundary but still rejects bursts that a bucket handles naturally. A leaky bucket as a queue shapes traffic by delaying requests, which adds latency we do not have budget for; as a meter it is equivalent to a token bucket with no burst headroom. The token bucket also needs only two numbers per customer (token count, last-refill timestamp), so state is tiny and updates are O(1).

**Where state lives and how regions share quota.** Each region runs the limiter inline in the API tier, holding bucket state in local memory, with a regional Redis (or equivalent) as the durable, shared-within-region copy. The hot path touches only local memory, which keeps added latency well under a millisecond, far inside the five-millisecond budget. A cross-region synchronous check would cost 50 to 150 ms and violate the constraint outright, so it is off the table.

To make three regions behave like one quota, split the customer's allowance by observed traffic. Each region starts with a share of the bucket (initially a third, or proportional to recent usage). Every 200 to 500 ms, regions broadcast their consumption deltas (tokens spent since the last sync) to the other two, and each region deducts remote consumption from its local bucket. Refill is computed locally from the clock, so only consumption needs replicating. A sync message is a few bytes per active customer, batched, so bandwidth is modest. An alternative is allocating token leases: a region requests a chunk of tokens (say 10 percent of the bucket) from a home region for that customer and spends it locally. Leases give a hard ceiling on overage but add complexity and strand tokens in idle regions; I would start with delta gossip and move to leases only if overage proves costly.

**What the inaccuracy is.** Between syncs, each region is blind to the others. Worst case, a customer whose requests are spread across all three regions can spend their full bucket in each region before any sync lands, getting up to roughly 3x the allowance in a single burst (1,800 requests on a 600 plan) in the first sync interval. Typical overage is far smaller, because DNS and load balancing rarely spread a two-second burst evenly, and with proportional shares (each region starting with a third of the bucket) the worst case drops to roughly the true quota plus whatever one region can spend before its first sync, on the order of 5 to 15 percent in realistic traffic. Over a full minute the error washes out, since deductions converge after each sync and refill is capped at the true rate. The opposite error also exists: after a sync a region may be slightly too strict, rejecting a request the true global state would allow, for a few hundred milliseconds. I consider both acceptable for an API whose purpose is protecting capacity, not metering billing. Anything billed per request must be counted separately from this limiter, from request logs.

**When the state store is slow or down.** The limiter must never be on the critical failure path. Rules: every call to Redis or the cross-region channel has a hard timeout of 2 ms, and the request path never waits on replication. If the regional store is slow or unreachable, the region keeps enforcing from its in-memory bucket, which is already authoritative for the hot path, and queues deltas for later. If a node restarts and has lost memory, it initialises buckets from the regional store; if that is also down, it starts each customer with a conservative bucket (say 25 percent of capacity, refilling at the plan rate) so a cold limiter cannot admit an unbounded flood. If the cross-region channel is partitioned, each region enforces only its local share plus a safety margin, so a customer can exceed quota by at most about 3x but the API stays up. A circuit breaker trips after repeated timeouts, stops calling the store for 5 to 10 seconds, then probes. In every failure mode the default is fail open to a degraded local limit, never fail closed. Clients see nothing unusual: no extra errors, perhaps slightly looser enforcement. The one exception is a global safety valve: a coarse per-region overall cap, independent of customer state, protects the backend if every limiter degrades at once.

**What clients see.** Every response carries the IETF draft headers RateLimit-Limit (plan allowance and window), RateLimit-Remaining (tokens left in the serving region's view), and RateLimit-Reset (seconds until the bucket would be full). Because remaining is a regional estimate, document it as approximate. Rejected requests return 429 Too Many Requests with a Retry-After header in seconds, computed from the bucket: time until one token is available, rounded up, plus a small random jitter of up to a second so that a burst of rejected scheduled jobs does not retry in lockstep. The body carries a machine-readable error code and the plan limit. Publish the algorithm in docs, explaining that the bucket permits bursts up to the full minute allowance, and recommend exponential backoff honouring Retry-After.

**Open questions.** Is the 3x worst-case overage tolerable for the largest plans, or should those customers get region-pinned routing or leases? Do we need per-endpoint costs (a heavy endpoint spending several tokens)? Clock skew between nodes affects refill slightly; use monotonic local clocks for refill and treat gossip as deltas, not timestamps.
