# Rate limiting a public API for bursty clients across three regions

Chosen as the closest call. Problem `api-rate-limiting`.

## Problem

A company runs a public HTTP API in three regions behind a single global hostname; a client's consecutive requests can land in different regions. Paying plans allow between 600 and 6,000 requests per minute, free accounts 60. Many legitimate clients are bursty: a scheduled job may send its whole minute's allowance in two seconds and then go quiet. The team has been asked to add rate limiting that adds no more than about five milliseconds to a request and that never takes the API down when the limiter's own storage is slow or unavailable.

Design the rate limiter: the algorithm and why it fits bursty clients, where its state lives and how the three regions share a customer's quota, what happens when that state is slow or unreachable, and how clients learn their limits and when to retry. Be explicit about what the design gets wrong and by how much.

### Constraints

- The API runs in three regions behind one global DNS name; a client's requests may land in any region.
- Paying customers are limited by plan (for example 600 requests per minute); free clients to 60 per minute.
- Legitimate clients are bursty: a client may send its whole minute's quota in two seconds, then nothing.
- The limiter must not add more than about five milliseconds to a request, and the API must keep serving if the limiter's storage is unavailable.

### Success criteria

- A named limiting algorithm and why it suits bursty clients better than the alternatives.
- Where the limiter's state lives, how three regions see one customer's quota, and what inaccuracy that implies.
- What happens when the state store is slow or down, and what the client sees.
- How a client learns its limit and when to retry.

Recommendation: Implement a Local Token Bucket algorithm with asynchronous global aggregation and strict local hard caps. This design satisfies the <5ms latency constraint by performing all rate checks locally in memory, while ensuring API availability during storage outages through a fail-open policy bounded by hard limits.

Algorithm and Burst Support: The system uses the Token Bucket algorithm for each customer in every region. Unlike Sliding Window Logs, which require storing individual request timestamps and incur O(N) latency for cleanup, Token Buckets use O(1) math on a counter and timestamp. This allows clients to consume their entire minute's allowance (e.g., 60 requests for free, 600 for paying) in a burst as small as two seconds, perfectly matching the stated client behavior. The bucket refills continuously at the plan rate, enforcing the average limit over time.

State Distribution and Inaccuracy: State lives locally in each region's memory to avoid the >5ms network latency of synchronous global checks. Regions share the quota by asynchronously pushing usage deltas to a central store. This creates an inherent inaccuracy: if a client bursts simultaneously from all three regions, each region may serve up to the full local limit before seeing the others' consumption. The worst-case over-provisioning is three times the plan limit (e.g., 180 requests for a free tier), accepting this 200% deviation as the necessary trade-off for low latency and high availability.

Handling Storage Outages: When the central state store is slow or unreachable, the system fails open. This means global quota checks are bypassed, and the API continues to serve requests without returning 429 errors due to infrastructure failure. To prevent backend saturation during these outages, each region enforces a synchronous local hard cap (e.g., 10x the plan limit). This ensures that even if global limits are ignored, the total throughput per client remains bounded and does not overwhelm downstream services.

Client Communication: Clients learn their limits via standard HTTP headers. When the system is healthy, responses include X-RateLimit-Limit (the plan max), X-RateLimit-Remaining (current local count), and Retry-After only in 429 Too Many Requests responses. During storage outages, when the system fails open, X-RateLimit headers are omitted or set to null to prevent clients from relying on inaccurate local state. Clients must implement exponential backoff for any 429s received.

Explicit Trade-offs: The design admits two major inaccuracies. First, the fail-open policy means rate limits are ignored globally during outages, risking overuse by legitimate bursty clients. Second, the asynchronous sync allows up to 3x over-provisioning during concurrent multi-region bursts. Third, the local hard cap is a static safeguard; without precise backend capacity data, it may be too restrictive for some or too permissive for others. These trade-offs are accepted because they preserve availability and latency, which are hard constraints.

Synthesis Conclusion: This Local Token Bucket design meets all success criteria. It handles bursty traffic efficiently, distributes state with bounded inaccuracy, fails open safely during outages, and communicates limits clearly via standard headers while omitting them during failures to prevent stale-state attacks.

## Baseline answer

The recommended solution employs a hybrid approach combining an in-memory local counter with an asynchronous, eventually consistent distributed reconciliation layer, governed by the Token Bucket algorithm. The Token Bucket is explicitly chosen over alternatives like Fixed Window or Sliding Log because it natively supports burstiness without penalty. In a Fixed Window scheme, a client sending their entire quota in the first second of a window could be blocked from sending again until the next minute starts, which contradicts the requirement to allow bursts followed by quiet periods. A Sliding Log would require storing every individual timestamp, consuming excessive memory and adding significant latency for log sorting and pruning, violating the five-millisecond constraint. The Token Bucket allows a client to accumulate tokens up to their plan limit (e.g., 600) and consume them in rapid succession, while naturally rate-limiting future bursts by depleting the bucket. This fits bursty workloads perfectly because the 'bucket size' equals the total monthly/minute allowance, allowing immediate exhaustion followed by a slow refill based on the average rate.

For state management, each region runs an independent local instance of the Token Bucket for every customer ID. This ensures the absolute lowest latency, as the check against local memory is O(1) and typically takes microseconds, well within the five-millisecond budget. To handle the global nature of the API, a background reconciliation process runs in each region. This process periodically (e.g., every 10-30 seconds) communicates with a distributed, eventually consistent key-value store, such as Redis Cluster or DynamoDB, which holds the authoritative 'global balance' for each customer. When a request occurs, the local counter is checked and decremented immediately. The state is not read from the remote store during the critical path to avoid network latency. Instead, the local bucket acts as a speculative pre-approval. If the client has remaining tokens locally, the request proceeds. This decouples the high-frequency check from the slower, potentially unreliable network round-trip required for global consistency.

Because the three regions operate independently with local state, there is an inherent inaccuracy in quota enforcement known as 'over-subscription risk.' If a client sends requests to Region A and Region B simultaneously, both regions may allow the burst if their local tokens are available. This can result in the total usage exceeding the 600-request limit within a single minute window. To mitigate this, the system must implement a safety margin or a strict hard-cap at the global store level during reconciliation. For example, the local bucket might be sized to only 80% of the actual limit, reserving 20% for the reconciliation safety buffer. Alternatively, a 'leaky' mechanism can be used where excess tokens are simply discarded and flagged for review if they breach the global hard limit. The inaccuracy is predictable: in the worst case, a bursty client could exceed their limit by approximately the size of the synchronization window multiplied by the max burst rate across regions. However, given the 60-second window and typical reconciliation intervals, this over-subscription is usually minor and acceptable for most business logic, provided the backend services can handle occasional overages.

The critical constraint of keeping the API up when the state store is slow or unavailable is addressed through a 'fail-open' design pattern combined with aggressive local caching. If the distributed store (Redis/DynamoDB) is unreachable or responds slowly, the local regions continue to operate based solely on their last known good state or a static default limit. The local counter does not depend on remote validation for every request; it only reports its delta to the remote store in the background. If the store is down, the reconciliation fails silently. The API assumes the client has quota and allows requests to proceed. This ensures availability (AP in CAP terms) at the cost of consistency (CP). For paying customers, this might lead to temporary overages that are billed later or capped in the next billing cycle. For free accounts, hard limits can be enforced locally via a simple static counter reset every minute, which is immune to remote store failures. The five-millisecond latency budget is preserved because no network call is made during the request handling phase; the 'slow' store is only contacted asynchronously by the reconciliation thread.

However, this design has explicit flaws. The primary weakness is the potential for significant over-granting of tokens due to the lack of real-time global synchronization. A malicious or buggy client could exploit the independence of regions to consume double their quota. Additionally, the 'fail-open' approach means that if a client exceeds their hard limit, they are not blocked until the next reconciliation cycle, potentially causing downstream service degradation. To counter this, one might argue for a more aggressive local limit reduction, but this hurts legitimate bursty users who might hit the lower local cap while the global store is unavailable. The trade-off is that we sacrifice precision for availability and low latency. Another flaw is the 'thundering herd' effect during recovery: when the store comes back online, all regions attempt to sync simultaneously, potentially overwhelming the store again. This can be mitigated by adding jitter to the synchronization intervals, but it remains an operational risk.

Client learning of limits and retry behavior must be handled via HTTP headers and standard status codes, independent of the internal state mechanism. The API should return a `Retry-After` header in milliseconds or seconds when a rate limit is hit, alongside a `429 Too Many Requests` status code. For the global hostname, the client cannot know which region served the request unless the response includes region metadata (which should be avoided for simplicity). Instead, the client implements exponential backoff with jitter, as recommended by best practices. The client should inspect the `X-RateLimit-Limit`, `X-RateLimit-Remaining`, and `X-RateLimit-Reset` headers in every successful response to understand their current standing. Since the local counter is speculative, these headers may be inaccurate if the global store rejects excess later. Therefore, clients must treat the `429` response as the ground truth for blocking. If a client receives a `503 Service Unavailable` from the API (indicating the limiter or backend is fully down), they should implement immediate retry with backoff, as this is a transient failure. The design ensures that clients can distinguish between 'rate limited' (429) and 'system down' (503/timeout), allowing them to adapt their burst behavior dynamically.

In summary, the Token Bucket algorithm running locally with asynchronous distributed reconciliation provides the best balance of burst support, low latency, and fault tolerance. It avoids the rigidity of fixed windows and the complexity of sliding logs. The state lives in local memory per region, sharing a customer's quota through eventual consistency via a background sync to a central store. This introduces a risk of over-quota usage during concurrent bursts across regions, which is mitigated by sizing local buckets slightly below the hard limit or accepting minor overages as a business trade-off. When the state store fails, the system fails open, allowing requests to proceed based on local state, ensuring the API remains available. Clients learn their limits through standard HTTP headers and handle retries via exponential backoff, treating 429 responses as signals to pause and 503s as signals of systemic failure. While not perfect due to potential over-subscription and reconciliation lag, this design robustly meets the five-millisecond latency and high-availability constraints.
