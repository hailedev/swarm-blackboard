# Rate limiting a public API for bursty clients across three regions

Chosen as the baseline's widest win. Problem `api-rate-limiting`.

## Problem

A company runs a public HTTP API in three regions behind a single global hostname; a client's consecutive requests can land in different regions. Paying plans allow between 600 and 6,000 requests per minute, free accounts 60. Many legitimate clients are bursty: a scheduled job may send its whole minute's allowance in two seconds and then go quiet. The team has been asked to add rate limiting that adds no more than about five milliseconds to a request and that never takes the API down when the limiter's own storage is slow or unavailable.

Design the rate limiter: the algorithm and why it fits bursty clients, where its state lives and how the three regions share a customer's quota, what happens when that state is slow or unreachable, and how clients learn their limits and when to retry. Be explicit about what the design gets wrong and by how much.

### Constraints

- The API runs in three regions behind one global DNS name; a client's requests may land in any region.
- Paying customers are limited by plan (for example 600 requests per minute); free clients to 60 per minute.
- Legitimate clients are bursty: a client may send its whole minute's quota in two seconds, then nothing.
- The limiter must not add more than about five milliseconds to a request, and the API must keep serving if the limiter's storage is unavailable.

### Success criteria

- A named limiting algorithm and why it suits bursty clients better than the alternatives.
- Where the limiter's state lives, how three regions see one customer's quota, and what inaccuracy that implies.
- What happens when the state store is slow or down, and what the client sees.
- How a client learns its limit and when to retry.

## Swarm answer

_Run `01a1e6fe-a341-7741-bf65-3bfba6abaa88`, 12 rounds, completed/budget_rounds, $0.0188, confidence 0.50; the final write-up, asked for about 900 words, 683 written._

Recommendation: enforce each customer's limit with a per-customer token bucket keyed by authenticated user ID, with capacity equal to the plan limit (600 per minute for paid plans, 60 per minute for free) and a refill rate of capacity divided by 60 tokens per second (10 per second paid, 1 per second free). A token bucket lets a bursty client spend its full minute's allowance in two seconds and then wait, which a fixed window or leaky bucket does not allow. Buckets start full so a scheduled job's first burst is honoured.

Algorithm fit: a fixed window would split a two-second burst across window edges and either reject legitimate work or let a client double its quota around a boundary. A sliding window log is accurate but stores one timestamp per request, which is too heavy at 6,000 requests per minute across three regions. A token bucket needs only a token count and a last-refill timestamp per customer, so it is cheap to update and naturally expresses 'burst up to the full minute, then steady refill'.

State and regions: each region keeps a local bucket on the request path so the limiter adds only in-process work, typically well under 1 ms and comfortably inside the 5 ms budget. Each region's bucket is periodically reconciled against a shared regional store, with a short sync interval of roughly 100 to 500 ms, so that one customer's quota is drawn down across regions rather than tripled. Assumption: the sync cadence keeps regional buckets close enough to the shared count that a client spread across regions is held near its plan limit most of the time; this rests on regional traffic being fairly even and on clocks being kept in step.

Accuracy and what it costs: during healthy operation a client whose requests land in all three regions can exceed its plan limit by the amount it can draw in one sync interval per region, which is bounded but not zero. Under a total store outage, each region can admit up to its share of the plan, and the worst case is roughly three times the plan limit per minute for a client spreading across regions evenly. The design accepts this rather than blocking requests. Multi-account abuse is a separate weakness: rotating accounts or keys defeats per-customer buckets. Assumption: this is contained by throttling account creation per IP and per payment method, which must be designed separately.

Store failure: when the shared store is slow or unreachable, the limiter must not block requests. Each region has a hard timeout on store calls of about 2 ms, and on timeout or error it falls back to the local bucket alone, admitting requests against a per-region share of the plan (roughly one third of the plan's rate) so that the API keeps serving and the backend load stays bounded. Requests are admitted, not rejected, in this mode. The client sees normal responses with the usual rate-limit headers, and a metric and alert fire so operators know the fallback is active.

Client contract: every response carries RateLimit-Limit (the plan limit), RateLimit-Remaining (whole tokens left) and RateLimit-Reset (seconds until the bucket will hold at least one token again, not until it is full). A rejected request returns 429 Too Many Requests with a Retry-After header in whole seconds. Clients should retry no earlier than Retry-After and use linear backoff with jitter rather than exponential backoff, since exponential backoff leaves quota unused after recovery. A scheduled job that has exhausted its allowance should resume at the steady refill rate, spreading remaining work evenly across the minute instead of bursting again.

Known weaknesses, stated plainly: regional skew and clock drift cause bounded over-admission during healthy operation; outage admission can reach about three times the plan limit for a multi-region client; first-minute burst allowances for new accounts are only a partial abuse control; and the exact meaning of RateLimit-Reset during fallback mode still needs to be fixed before launch. Confidence is moderate: the algorithm choice is well supported, while the cross-region accuracy bound and the account-abuse control are the parts most likely to change.

## Baseline answer

_claude-haiku-5-5, asked for about 900 words, used 1718 of 2693 output tokens allowed under a $0.0300 cap, cost $0.0010. Board handles are shown here; the judge saw the answers with them removed._

Recommendation: enforce each customer's quota with a token bucket whose capacity equals the plan's per-minute allowance and whose refill rate is that allowance divided by sixty seconds, so a paying customer on 600 requests per minute gets a bucket of 600 tokens refilling at 10 per second. Keep the bucket state in a regional in-memory store that is replicated asynchronously across the three regions, and make the limiter fail open: if the store is slow or unreachable within a strict budget, the request proceeds and the limiter records the miss. This meets the five-millisecond budget and the requirement that the API keep serving, at the cost of approximate global enforcement.

Why a token bucket fits bursty clients: a bucket lets a client accumulate up to a full minute's allowance while idle and spend it at once, so a scheduled job that sends 600 requests in two seconds is admitted in full and then throttled until tokens refill. A fixed-window counter also admits bursts, but it has the boundary problem, where a client can send its quota at the end of one window and again at the start of the next, briefly doubling its rate. A sliding-window log is accurate but stores a timestamp per request, which is expensive at 6,000 requests per minute across many customers. A leaky bucket smooths output and would delay or reject the legitimate burst, which is the wrong behaviour for this population. The token bucket therefore gives the burst tolerance the clients need and a hard long-run ceiling.

State and regions: each bucket is keyed by customer identifier and plan, and holds two numbers, the token count and the last update time. The request path in each region reads and updates its local copy with a single atomic operation, which is what keeps the limiter within five milliseconds; a cross-region round trip would exceed that budget on its own. Regions exchange their consumption counts in the background, every second or so, so each region gradually learns how much of the customer's quota the others have spent. Because a client's requests can land anywhere, the design divides the quota: each region is allotted roughly one third of the plan limit as its local bucket, with rebalancing when one region is consistently exhausted while others are idle. The inaccuracy this implies is concrete. Between synchronisation rounds a customer can spend up to the sum of regional allotments plus whatever each region admits from stale peer information, so a customer whose requests spread evenly across regions may exceed the plan by something on the order of ten to twenty percent in a bad second, and a customer that concentrates on one region may be throttled earlier than its true global quota because that region's share is exhausted while others hold spare capacity. Over a full minute the overage is bounded by the replication lag times the request rate, which is small for a one-second lag, but it is not zero, and the design should be presented to the business as approximately enforced.

Failure behaviour: the limiter wraps every store call in a timeout of about two milliseconds, well inside the budget. If the store does not answer in time, or the call errors, the request is admitted and the event is counted in a local metric and a sampled log. A circuit breaker opens after a short run of failures so that a degraded store stops adding latency to every request and the limiter does not retry into a stalled dependency; it probes periodically to close again. The consequence the team must accept is that during an outage the limit is not enforced at all. A customer who would have been throttled is served, which costs the operator capacity and may breach a paid tier's terms, but the alternative, failing closed, would turn a storage fault into a full API outage for every customer, which is the outcome the requirement forbids. If enforcement during an outage matters, a coarse per-region fallback limit held in process memory, generous enough to protect the fleet but not tuned to any plan, is a reasonable middle ground.

What clients see and how they learn their limits: every response carries headers stating the plan limit, the remaining tokens, and the time until the bucket is full again, using the conventional RateLimit-Limit, RateLimit-Remaining and RateLimit-Reset fields, with the limit and reset also visible in the account dashboard. When a request is rejected, the API returns 429 Too Many Requests with a Retry-After header giving the number of seconds until one token is available, computed from the refill rate, which for a 600-per-minute plan is about 0.1 seconds. Clients should retry after that interval with jitter rather than immediately, and should be told that a burst equal to the full bucket will succeed. Free clients at 60 per minute refill one token per second, so their Retry-After values will be correspondingly longer. Because the limiter can fail open, a 429 is always a genuine decision based on the best available information, but a client should not assume that the absence of a 429 during an incident means its quota is unlimited.

Open questions and caveats: the replication interval, regional quota split and circuit-breaker thresholds are tunable and should be set from load tests, not from the numbers above, which are reasoned estimates. The team should measure the actual overage under a deliberately skewed traffic split before committing to the approximate-enforcement position with customers. If the business later requires exact global enforcement, the design would need a single authoritative counter, which cannot meet the five-millisecond budget across three regions without giving up either latency or availability, so that trade-off should be made explicit now rather than discovered later.
