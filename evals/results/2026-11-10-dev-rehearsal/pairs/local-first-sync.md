# Storage and sync for a local-first notes app

Chosen as the baseline's widest win. Problem `local-first-sync`.

## Problem

Two developers are building a local-first notes app: text notes with attachments up to 10 MB, on phones and laptops, fully usable offline. They have no server today and want none for the first release, but they plan to offer a paid hosted sync service within a year. Customers will often edit the same note on two devices before either has connected, and they expect not to lose text when that happens.

Recommend how the app should store data on the device and how it should sync, how concurrent edits are reconciled and what the user sees when they conflict, and how the team gets from "no server" to a hosted sync service without existing users having to migrate anything. Name the risks of your recommendation and how the team would find out early if one of them is real.

### Constraints

- The app must work fully offline on phone and laptop; sync is a convenience, never a requirement.
- Two developers; the first paying customers are expected in six months.
- Notes are text with attachments up to 10 MB; users expect edits on two devices at once not to lose text.
- The team wants to start with no server and add a hosted sync service later without migrating users' data by hand.

### Success criteria

- A recommended on-device storage choice and a sync strategy, with the alternatives rejected and why.
- How concurrent edits on two devices are reconciled, and what the user sees when they conflict.
- A migration path from no server to a hosted service that existing users do not notice.
- The main risks of the recommendation and how to find out early whether they bite.

Recommendation: Adopt Yjs as the local-first sync engine with `y-indexeddb` for persistent storage on both mobile and laptop. This choice satisfies the requirement for handling up to 10MB attachments efficiently via native `Y.Blob` support, avoiding the serialization overhead and performance risks associated with Automerge (H12, H16, H30). The local data model is a single YDoc document stored in IndexedDB, which allows for seamless future migration to a hosted service without data transformation or user intervention (H22, H24, H29).

Sync Strategy: Implement an event-driven sync loop where the client listens to local `update` events and pushes deltas/blobs to a Neutral Relay asynchronously. The Neutral Relay acts as a 'Versioned Blob Store' rather than a simple Last-Writer-Wins store (H25, H27). It stores multiple divergent YDoc buffers for each Note ID, keyed by client vector or timestamp. This ensures that no edits are lost during network partitions; if two devices upload conflicting versions, the server keeps both, allowing the clients to fetch all necessary blobs and deterministically merge them using Yjs's CRDT logic (H23, H27).

Conflict Reconciliation & UI: Rely on Yjs's automatic deterministic merge for text changes, which prevents data loss without complex LWW strategies. However, because automatic merging can produce unintelligible results in edge cases (e.g., concurrent deletions), implement a 'Transparent Merge with Manual Override' UI pattern (H26). Users will see a 'Show Changes' button that displays a side-by-side diff of local vs. server state when divergence is detected. This allows users to manually resolve conflicts, ensuring no text is lost and providing peace of mind during the transition from offline to online states.

Migration Path: The architecture starts as 'Local-Only' with no server dependency. Existing YDoc structures in IndexedDB are preserved. When the hosted sync service launches, the app simply connects to a new HTTP endpoint that accepts/returns full YDoc buffers (H24). No schema migration is required because the binary format is identical locally and remotely. To prevent 'conflict storms' during initial sync after long offline periods, implement periodic snapshotting (H24), where full snapshots are uploaded and downloaded periodically to reduce bandwidth usage and keep the delta history manageable.

Risks & Validation: The primary risk is performance degradation on mobile devices when syncing large 10MB attachments over cellular networks. Validate this early by building a 'Mock Server' that echoes back data via HTTP GET/POST (H5, H29) and testing the Yjs sync loop with simulated network partitions. A secondary risk is the complexity of implementing a Versioned Blob Store on the server; mitigate this by starting with a simple LWW fallback in the mock server and refining to versioning only if split-brain conflicts are observed during testing (H23, H27). If write latency exceeds 100ms for 10MB files, refactor to a hybrid storage model where blobs are chunked locally before sync.

The recommended on-device storage architecture for this local-first notes app is CRDT-based (Conflict-free Replicated Data Type) embedded directly within a robust, native database engine such as SQLite or Realm, augmented by a content-addressable storage layer for attachments. We reject the idea of using a simple key-value store or flat files because they lack the semantic structure required to handle complex text edits and concurrent modifications reliably. We also reject centralized server-side databases like PostgreSQL for the initial phase because the constraint explicitly forbids a server, and building a custom replication protocol from scratch without CRDT semantics is prone to data loss. Instead, we utilize a CRDT library that operates on operational transforms or sequence-based models (such as Yjs, Automerge, or Dat) which are specifically designed for offline-first scenarios. These libraries maintain a state vector for each document, allowing multiple devices to modify the same note independently and then reconcile those changes deterministically upon reconnection. For attachments up to 10MB, we recommend storing files in the device’s filesystem with their SHA-256 hashes as filenames or keys in a local index. This approach ensures data integrity without duplicating storage efforts and allows for efficient deduplication when syncing later.

Regarding the sync strategy, the system must support peer-to-peer synchronization that does not require an initial server handshake. We recommend implementing a 'sync engine' that acts as a middleware layer between the UI and the local database. This engine will expose a standard interface for pushing and pulling changes based on state vectors. When a device goes offline, all edits are applied locally to the CRDT instance. The sync engine queues these changes in a local transaction log. When network connectivity is restored (or when devices are physically close via Bluetooth/Wi-Fi Direct for local sync), the engine initiates a peer-to-peer exchange of state vectors. It identifies divergent versions of each note, applies the CRDT merge algorithm to resolve conflicts at the byte or block level, and updates the local database accordingly. We reject simple file syncing (like Dropbox-style) because it is binary-opaque and cannot handle concurrent text edits without overwriting one user's work entirely. The P2P approach allows for immediate utility offline and lays the groundwork for server-mediated sync later by treating the future server as just another peer in the graph of available storage locations.

Concurrent edit reconciliation should be handled automatically by the CRDT logic, ensuring that no text is lost. For text notes, we recommend using a block-based or character-level CRDT such as Yjs’s YXML/YText or Automerge. These systems allow two users to insert characters at different positions without conflict, and if they insert at the same position, the system uses a deterministic tie-breaking rule (such as session ID or logical clock) to order the characters. The user should never see a 'merge conflict' UI for text unless the edit involves structural changes that are semantically ambiguous (e.g., one user adds a header while another deletes it). In such cases, the CRDT merges both additions if they can coexist, or keeps them separate if they cannot. If the system encounters a true semantic conflict where two versions of a note diverge irreconcilably, the app should present a unified view showing both versions side-by-side or in a thread, allowing the user to manually select the preferred version. However, for 95% of text edits, the reconciliation should be silent and automatic, preserving all characters from both devices.

The migration path from 'no server' to a hosted sync service must be seamless and require no manual migration for existing users. The key insight is to design the initial local storage structure to be compatible with the eventual remote storage schema. Initially, the app will have a 'local-only' mode where the CRDT state is stored solely on the device. We will introduce a virtual 'sync peer' concept in the codebase from day one. When the hosted service launches, it will act as a new sync peer for existing clients. The client’s sync engine will already be capable of negotiating with multiple peers. To migrate users, we do not need to move their data; we simply need to make their local CRDT state available to the server. We can achieve this by having the app periodically (or on-demand) upload a 'state snapshot' or delta log to the new hosted service. The server stores these snapshots in a cloud-compatible format. Future devices can sync with the server, and existing devices can also sync with the server once they connect. Crucially, because CRDTs are commutative and associative, the order of synchronization does not matter. An existing user who edits on Device A while offline can later sync with the hosted service; the server will merge Device A’s changes with any other device that has already synced with it. There is no 'migration' of data files; rather, the data becomes distributed across multiple reliable peers.

A critical risk in this architecture is the 'storage explosion' problem inherent in CRDTs. As users edit notes extensively, the internal history (or log) within the CRDT structure can grow indefinitely, leading to bloated local storage and slow sync times. To mitigate this, we must implement a compaction strategy where the CRDT periodically merges its internal operations into a single state snapshot, pruning redundant history. Another risk is the complexity of debugging conflict resolution logic. Since conflicts are handled algorithmically rather than manually, bugs in the merge function can lead to silent data corruption or loss. The team must also consider the security of attachments; storing 10MB files locally without encryption exposes sensitive data if the device is stolen. We recommend implementing end-to-end encryption for the sync channel and local storage encryption.

The second major risk is the complexity of implementing a robust P2P sync engine from scratch. Developing a custom CRDT backend can be time-consuming for two developers. An alternative approach might involve using existing frameworks like Joplin or Standard Notes’ open-source models, but these may be too heavy or restrictive. A third risk is the 'split-brain' scenario where devices are connected to different servers or no server at all, leading to divergent histories that are difficult to reconcile without a central truth. To address this, we must ensure that the CRDT choice supports multi-peer consistency and that the sync protocol allows for efficient resolution of divergences.

To mitigate these risks, the team should conduct rigorous unit testing of the CRDT logic with edge cases involving concurrent insertions, deletions, and moves. They should also perform load testing to measure storage growth over time. For the migration risk, they can simulate the transition by introducing a dummy server early on to test the client’s ability to sync with multiple peers. Regular user feedback loops are essential to verify that the 'silent' conflict resolution meets user expectations for data preservation.

The recommended storage choice is a hybrid of a relational-like local database (SQLite/Realm) for metadata and attachments, coupled with a CRDT engine (like Yjs or Automerge) for text content. This separation allows efficient querying of notes while preserving the flexibility of CRDTs for text editing. We reject pure NoSQL local databases because they lack native support for complex text structures. We also reject cloud-only solutions because they violate the offline-first constraint. The sync strategy relies on state-vector based peer-to-peer exchange, ensuring that changes are applied deterministically regardless of network topology.

Concurrent edits are reconciled automatically by the CRDT algorithm, which treats text as a sequence of characters or blocks with unique IDs. If two users edit the same character, the system uses a deterministic tie-breaker to order them. If edits are non-overlapping, they are both preserved. The user sees no conflict unless the edit involves structural changes that cannot be merged semantically. In such cases, the app presents a 'merge view' showing both versions side-by-side, allowing the user to choose or manually merge. This approach minimizes user friction while ensuring data integrity.

The migration path leverages the commutative property of CRDTs. Existing users’ local data remains untouched. When the hosted service launches, it registers as a new peer. Clients automatically sync with this peer when online. The server stores snapshots or deltas in a compatible format. Future devices can sync with the server, and existing devices continue to function locally while syncing with the server when possible. There is no manual migration; the data simply becomes accessible via a new reliable peer.

Key risks include storage bloat due to CRDT history growth, complexity of implementing P2P sync correctly, and potential for silent data corruption in conflict resolution. Mitigation strategies include implementing periodic compaction of CRDT logs, using well-tested open-source CRDT libraries where possible, and extensive testing with simulated concurrent edits. The team should also plan for end-to-end encryption to protect sensitive data.

Early validation can be achieved by building a prototype that simulates offline editing on two devices and then syncing them via a local network or file exchange. This tests the core CRDT logic and sync protocol without needing a server. The team can also conduct user testing with mock 'conflict' scenarios to ensure the UX is clear and data preservation is effective. Monitoring storage growth metrics during development will help identify potential bloat issues early.

In conclusion, this approach balances the need for robust offline functionality with future scalability. By using CRDTs for text and a hybrid local database structure, the app ensures data integrity and flexibility. The P2P sync strategy facilitates a seamless transition to hosted services. Risks are managed through careful architecture choices, rigorous testing, and user-centric design. This plan supports the team’s constraints while paving the way for sustainable growth.
